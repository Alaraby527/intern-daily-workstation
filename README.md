# 实习生每日工作台

> 一个面向实习团队的任务执行与打卡闭环系统。实习生按业务线查看每日 SOP、勾选任务、提交打卡，数据自动同步飞书多维表格；Mentor 在后台验收。

---

## 一、业务背景

### 1.1 真实痛点

团队有 12 名实习生，分布在 A/B/C/D/E 五条业务线（创作者触达、官方账号、社群爆款、内容供给、情报产品），每条线有不同的北极星指标和每日 SOP。Mentor 团队面临以下问题：

| 痛点 | 具体表现 | 影响 |
|------|----------|------|
| **执行标准不统一** | 实习生靠口头/群消息接收任务，不知道"做完"的标准是什么 | 交付质量参差，Mentor 反复追问 |
| **打卡分散在多处** | 任务在群里、交付物在表格、日报在群消息，Mentor 要跨 3-4 个地方核对 | 验收耗时，容易遗漏 |
| **新人上手成本高** | 每条线有 4-6 个每日任务 + 多个子表，新人第一周频繁问"这个填哪张表" | Mentor 被重复问题打断 |
| **完成状态不可见** | Mentor 无法实时看到谁做了什么、卡在哪里 | 问题暴露滞后，周会才发现缺口 |
| **数据回填手动操作** | 实习生需要手动在多张飞书多维表格中填写记录 | 重复劳动，漏填错填率高 |

### 1.2 为什么值得解决

- **高频**：每个实习生每天都要执行 SOP 任务并打卡，一天 2 次以上触达系统
- **可量化**：打卡率、验收时效、同步成功率均可追踪
- **可复用**：任务配置化，新业务线只需改数据文件，不改代码

## 二、用户场景

### 2.1 目标用户

| 角色 | 人数 | 核心诉求 |
|------|------|----------|
| 实习生 | 12 人 | 清楚知道今天做什么、怎么做、做完填哪里 |
| Mentor | 3-5 人 | 快速看到所有人的打卡和交付物，完成验收 |

### 2.2 核心场景（只保留一个）

**实习生每日开工 → 执行任务 → 打卡提交 → Mentor 验收**

> 实习生早上打开工作台，系统自动识别身份并展示其所属业务线的当日任务。按上午/下午/下班前分组执行，勾选完成、上传产出物链接。下班前填写当日目标完成量和卡点，一键提交。数据自动写入飞书多维表格，Mentor 在验收台看到所有方向的打卡记录，逐条验收。

### 2.3 不做什么

- 不做即时通讯（复用飞书群）
- 不做任务分配/排期（SOP 是固定的，不需要灵活派发）
- 不做数据报表 Dashboard（Mentor 要的是验收动作，不是看图表）

## 三、人机方案

### 3.1 分工边界

| 环节 | 系统自动 | 人工确认 |
|------|----------|----------|
| 身份识别 | 飞书客户端内自动获取用户身份，匹配实习生名单 | 匹配失败时手动下拉选择 |
| 任务展示 | 根据业务线配置自动渲染任务列表、完成标准、SOP 链接 | — |
| 产出物关联 | 自动关联任务对应的飞书子表，一键跳转填写 | 实习生自行确认填写内容 |
| 数据同步 | 提交后通过飞书开放平台 API 自动写入多维表格 | — |
| 同步失败 | 自动记录失败状态和错误信息，支持一键重试 | Mentor/管理员排查配置问题 |
| 验收 | — | Mentor 逐条审核，通过/需改进，填写反馈 |

### 3.2 人工卡点设计

1. **身份匹配失败** → 降级为手动选择，不自动猜测身份
2. **同步失败** → 不丢数据，本地保留记录并标记"同步失败"，可重试
3. **Mentor 验收** → 打卡提交后状态为"待验收"，必须 Mentor 手动确认才闭环

### 3.3 为什么不用大模型

本项目的核心场景是**结构化任务的执行追踪与数据回填**——任务是预定义的 SOP，打卡是结构化字段（目标量、完成量、备注），同步目标是确定的多维表格。这类场景规则明确、输入输出确定，用表单 + 工作流 + API 集成即可解决。如果硬套对话式 AI：

- 任务勾选和数量填写用表单比对话更高效、更不易出错
- 数据同步要求字段精确匹配，LLM 生成反而引入幻觉风险
- 实习生每天重复使用，表单的肌肉记忆优于对话交互

> 产品判断：在确定性高的场景用确定性方案，把 AI 留给真正需要理解非结构化信息的环节。

## 四、技术方案设计

### 4.1 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 前端 | React + TypeScript + Vite | 组件化适合任务卡片/表单等重复 UI；Vite 启动快 |
| 样式 | Tailwind CSS + CSS 变量 | 快速实现设计系统，支持业务线语义色 |
| 后端 | NestJS + TypeScript | 模块化架构，与前端共享类型定义 |
| 数据库 | SQLite + Drizzle ORM | 零运维，本地存储任务进度和打卡记录 |
| 外部集成 | 飞书开放平台 API | 多维表格写入、电子表格读取、Bot 身份认证 |

### 4.2 系统架构

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  实习生前端   │────▶│  NestJS 后端  │────▶│  飞书多维表格 API │
│  (React)    │◀────│  (NestJS)    │◀────│  (Bitable API)  │
└─────────────┘     └──────┬───────┘     └─────────────────┘
                           │
                     ┌─────┴─────┐
                     │  SQLite   │
                     │ (本地缓存) │
                     └───────────┘
```

- 前端负责任务展示、勾选、表单填写
- 后端负责业务逻辑、飞书 API 调用、数据持久化
- SQLite 作为本地缓存，保证飞书 API 失败时数据不丢
- 飞书多维表格是最终数据源，Mentor 可在飞书内直接查看

### 4.3 关键技术决策

**1. 飞书同步用 Bot 身份而非用户身份**

所有 API 调用使用 `tenant_access_token`（应用身份），不依赖实习生个人的多维表格权限。实习生只需能打开应用，不需要被加为多维表格协作者，降低权限管理成本。

**2. 任务配置化而非硬编码**

实习生名单（`interns.ts`）、业务线配置（`lines.ts`）、任务定义（`tasks.ts`）、任务与子表映射（`task-table-map.ts`）全部抽离为独立数据文件。新增业务线或调整任务不需要改组件代码。

**3. 本地优先 + 异步同步**

打卡提交先写入本地 SQLite，再异步同步飞书。同步失败时记录错误状态，用户可重试。避免飞书 API 抖动导致用户提交失败。

**4. 身份自动识别 + 手动降级**

通过平台注入的 `req.userContext` 获取飞书用户名，在实习生名单中精确匹配。未匹配或未登录时降级为下拉选择，保证任何场景下都能用。

## 五、流程闭环

### 5.1 核心流程

```
实习生打开工作台
    │
    ├─ 飞书客户端内 ──▶ 自动获取身份 ──▶ 匹配名单 ──▶ 进入任务页
    │                                              │
    └─ 客户端外/未命中 ──▶ 手动选择姓名 ─────────────┘
                                                   │
                                    ┌──────────────▼──────────────┐
                                    │  展示所属业务线的当日 SOP 任务  │
                                    │  (北极星指标 + 分时段任务)     │
                                    └──────────────┬──────────────┘
                                                   │
                                    ┌──────────────▼──────────────┐
                                    │  执行任务：勾选/上传附件/填链接 │
                                    └──────────────┬──────────────┘
                                                   │
                                    ┌──────────────▼──────────────┐
                                    │  下班前填写打卡：目标/完成量/卡点│
                                    └──────────────┬──────────────┘
                                                   │
                                    ┌──────────────▼──────────────┐
                                    │  提交：先存本地，再同步飞书     │
                                    │  成功 → 显示"已同步"           │
                                    │  失败 → 标记"同步失败"，可重试  │
                                    └──────────────┬──────────────┘
                                                   │
                                    ┌──────────────▼──────────────┐
                                    │  Mentor 验收台：查看所有打卡   │
                                    │  通过 / 需改进 + 反馈          │
                                    └─────────────────────────────┘
```

### 5.2 异常兜底

| 异常场景 | 兜底策略 |
|----------|----------|
| 飞书 API 超时/限流 | 本地保存成功，标记"同步中"，后台重试 |
| App Secret 失效 | 同步失败并展示具体错误信息，引导管理员检查配置 |
| 身份获取失败 | 降级为手动下拉选择，不阻断使用 |
| 多维表格字段变更 | 同步失败并记录飞书返回的字段错误，便于排查 |
| 重复提交 | 同一实习生同一天只保留一条打卡记录，再次提交走更新逻辑 |

### 5.3 数据模型

核心实体：

- **Intern**：姓名、所属业务线（可跨线）
- **Task**：标题、时段、时长、完成标准、步骤、产出物类型、关联子表
- **Checkin**：实习生、日期、业务线、目标量、完成量、卡点备注、验收状态、飞书记录 ID
- **BusinessRecord**：业务类型、关联任务、飞书记录 ID、同步状态、错误信息
- **FeishuBitableConfig**：App ID、App Secret、Base Token、启用状态

## 六、失败案例与迭代

### 6.1 失败案例：上线后全员无法同步

**现象**：管理员自己使用正常，但实习生提交打卡时全部显示"同步失败"，数据无法写入飞书多维表格。

**排查过程**：

1. 查看后端日志，飞书 API 返回 `10014 app secret invalid`
2. 检查数据库中存储的 App Secret，发现与飞书开放平台的凭证有**一个字符差异**
3. 管理员自己"能用"是因为数据保存在了本地 SQLite，实际上从未成功同步到飞书

**根因**：App Secret 在手动录入时发生字符错误，token 获取失败导致所有写操作被拒。

**修复**：
- 从飞书开放平台重新获取正确凭证，更新数据库配置
- 重启服务清空 token 缓存
- 修复后写入/删除测试记录验证通过
- 之前失败的记录通过"重试"按钮完成同步

**反思**：
- 凭证录入应有校验机制（如录入后立即调用一次 token 接口验证）
- "本地保存成功"给了管理员错误的安全感——应该在管理后台展示同步成功率监控
- 管理员自测时只验证了"提交不报错"，没有验证飞书表格里是否真的有数据

### 6.2 迭代记录

| 版本 | 改动 | 效果 |
|------|------|------|
| V1.0 | 基础功能：手动选名、任务勾选、打卡提交、飞书同步、Mentor 验收 | 跑通核心闭环 |
| V1.1 | 修复 App Secret 配置错误，恢复飞书同步 | 同步成功率从 0% 恢复到 100% |
| V1.2 | 新增飞书身份自动识别，打开应用直接进入工作台 | 减少 1 步操作，避免选错人 |
| V1.2 | 同步失败支持一键重试，不丢数据 | 失败记录可恢复，不用重新填写 |

### 6.3 仍未解决的问题

- 飞书多维表格字段变更时没有自动检测，需要手动更新表 ID 配置
- 没有同步成功率的监控看板，只能逐条看记录状态
- 任务进度保存在本地浏览器，换设备后勾选状态丢失
- 子表填写仍需跳转到飞书多维表格，没有在应用内内嵌表单

## 八、快速开始

```bash
# 安装依赖
npm install

# 启动开发服务器
npm run dev

# 构建生产版本
npm run build
```

### 飞书配置

1. 在[飞书开放平台](https://open.feishu.cn/)创建企业自建应用
2. 获取 App ID 和 App Secret，开通多维表格权限
3. 将应用添加为目标多维表格的协作者（编辑权限）
4. 在 Mentor 后台「飞书集成」面板中配置凭证

### 自定义

- 实习生名单：`client/src/data/interns.ts`
- 业务线配置：`client/src/data/lines.ts`
- 任务定义：`client/src/data/tasks.ts`
